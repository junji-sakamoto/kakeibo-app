# 品質チェックの手順書

プログラムと資料の品質を確かめる手順です。**コミットする前**と、**AWS に公開する前**に行います。
コマンドは、VS Code の画面下のターミナル（PowerShell）で、プロジェクトの一番上のフォルダ（`syokyu-kadai`）にいる状態で入力します。

## 1. まとめて確かめる（ふつうはこれだけ）

**先にデータベースを起動しておきます**（[データベースの手順書](01_データベースの手順書.md) の「2. 起動する」）。処理側・画面側は起動しなくて大丈夫です。

```powershell
node tools/quality_check.mjs
```

最後に、まとまりごとの結果の表が出ます。**「不合格 0」なら合格**です。不合格のときは、その項目のすぐ上に、原因を調べるための表示が出ます。

  2. プログラムとして読み込めるか（足りない部品や、つながっていないファイルがないか）

## 3. アンチパターンチェック

**アンチパターン**とは、「動くけれど、やってはいけない書き方」のことです。ESLint の一般的な決まりでは見つけにくい、**このアプリで決めた約束ごと**を、`tools/antipattern_check.mjs` が1行ずつ探します。

| 番号 | 探すもの（例） |
|---|---|
| AP-F01〜AP-F07（画面側） | `v-html`・`innerHTML`（XSS の危険）、ブラウザの小窓（`alert`・`confirm`）、`api.js` の外での `fetch`、処理側のアドレスの直接の書き込み、`console.log`・`debugger` の残し |
| AP-B01〜AP-B10（処理側） | SQL への値の埋め込み（SQL インジェクションの危険）、`SELECT *`、エラーのくわしい内容を返す、パスワードの直接の書き込み、エラーを捨てる `catch {}`、結果の番号を書かない `res.json` など |
| AP-I01〜AP-I10（インフラ） | どこからでも入れる門番（`0.0.0.0/0`）、パスワード・IP アドレス・メールアドレスの直接の書き込み、記録（ステート）に残るパスワードの渡し方、RDS の公開、暗号化なし、IMDSv1、http のままの CloudFront、版を固定しない AWS プロバイダー、イメージ番号の直接の書き込み |

- 見つかったときは、番号・場所（ファイル名と行の番号）・その行が表示されます
- それぞれの決まりの中身は、`tools/antipattern_check.mjs` の `FRONTEND`・`BACKEND`・`INFRA` に、説明と一緒に書いています（同じ内容を2か所に書かないため、この手順書には例だけを書きます）

## 4. 書き方のチェック（ESLint）の決まり

決まりは、`backend/eslint.config.js` と `frontend/eslint.config.js` に書いています。

| 決まり | 内容 | 理由 |
|---|---|---|
| ESLint のおすすめ（`recommended`） | 使っていない変数、書き間違いやすい書き方などを見つける | ESLint の標準 |
| Vue.js のおすすめ（`flat/recommended`）※画面側だけ | `.vue` ファイルの書き方の決まり | Vue.js の公式の標準 |
| `eqeqeq` | `==` ではなく `===` を使う | 思わぬ型の変換で、間違った比べ方になるのを防ぐ |
| `prefer-const`・`no-var` | 書き換えない変数は `const`、古い `var` は使わない | 今の JavaScript の標準の書き方 |
| `curly` | `if` などの `{ }` を、複数行のときは省かない | あとから行を足したときの間違いを防ぐ |
| `prefer-template` | 文字をつなぐときは `` `${ }` `` を使う | 読みやすくするため |
| `no-irregular-whitespace` | プログラムの中の全角の空白を見つける（日本語の文字や説明の中は許す） | 目に見えない間違いを防ぐ |

## 5. まとめて確かめることに入っていないもの

次のものは、必要なときに個別に確かめます。

| 確かめること | 方法 |
|---|---|
| 画面の見た目・操作 | 処理側と画面側を起動し、ブラウザで操作する（[フロントエンドの手順書](03_フロントエンドの手順書.md)） |
| 資料の図（Mermaid）が描けるか | GitHub で資料を開き、図が表示されるかを見る |
| 道具が見比べない資料の中身（入力のルール、画面の動き など） | 資料を読み、実装と見比べる（Claude Code の「品質チェック」スキルでも行える） |
| `mock/`（試作品）と `tools/`（道具）の書き方 | ESLint の対象に入れていない。直したときは、動かして確かめる |

## 6. Claude Code の「品質チェック」スキル

Claude Code に「**品質チェックをしてください**」と頼むと、[.claude/skills/quality-check/SKILL.md](../../.claude/skills/quality-check/SKILL.md) に書いた手順で、上の「1. まとめて確かめる」に加えて、**資料と実装の見比べ（人の目で）**と、**レビューポイント（RP-01〜RP-36）**の確認も行い、4つのまとまりごとに報告します。

- レビューポイントは、デファクトスタンダードから外れていないか、これまでに見つかった問題をまた起こしていないかを確かめる観点の一覧です。中身は、上のスキルのファイルの「3. レビューポイント」にまとめています（同じ内容を2か所に書かないため、この手順書には書きません）
- 新しい問題が見つかったときは、同じ問題を二度と見落とさないように、レビューポイントを足していきます
