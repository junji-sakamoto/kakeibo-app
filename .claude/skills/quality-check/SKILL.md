# 品質チェック（家計簿アプリ）

このプロジェクトの品質を、次の3段階で確かめて報告する。説明は**初心者にも分かる、やさしい日本語**で行う。

## 1. まとめて確かめる（自動）

1. データベースが起動しているか確かめる（`docker inspect -f "{{.State.Health.Status}}" kakeibo-db` が `healthy`）。起動していなければ、起動してよいか使う人に聞いてから `docker compose -f database/compose.yaml up -d --wait` で起動する
2. プロジェクトの一番上のフォルダで実行する：

   ```powershell
   node tools/quality_check.mjs
   ```

3. 確かめる内容（くわしくは `docs/03_手順書/04_品質チェックの手順書.md`）
   - Node.js の版（26 系）
   - LINT：`backend`・`frontend` の `npm run lint`
   - 試験：`backend` の `npm test`、`database/tests/check_rules.sql`
   - 組み立て：`frontend` の `npm run build`
   - 部品の弱点：`backend`・`frontend` の `npm audit`
   - 資料：`要件定義書.md` が最新か（`node tools/build_requirements.mjs --check`）、Markdown のリンク切れ
4. 不合格があれば、原因を調べる。**直す前に**、何が原因で、どう直すかを使う人に説明する

## 2. 資料と実装の見比べ（人の目で）

次の資料と実装を見比べ、食い違いを探す。**食い違っていたら、実装を正として資料を直す**のがこのプロジェクトの決まり（ただし、実装が要件を満たしていない＝不具合のときは、使う人に確かめてから実装を直す）。

| 資料 | 見比べる実装 |
|---|---|
| `docs/01_要件定義/04_機能要件.md`（入力のルール・並び順など） | `backend/src/validation.js`、`frontend/src/format.js`、各画面の `check()` |
| `docs/01_要件定義/05-0〜05-4`（画面要件） | `frontend/src/views/*.vue`、`frontend/src/App.vue`、`frontend/src/style.css` |
| `docs/01_要件定義/06_メッセージ一覧.md` | `frontend/src/messages.js`（文章はここ1か所だけ）、処理側が返す番号 |
| `docs/02_設計/02_画面遷移図.md` | `frontend/src/router.js`、画面の中の移り方 |
| `docs/02_設計/05_データの流れ.md`・`06_API設計書.md` | `backend/src/routes/*.js`、`frontend/src/api.js` |
| `docs/02_設計/04_テーブル定義書.md` | `database/sql/01_create_tables.sql` |
| `docs/01_要件定義/07_非機能要件.md` | 安全のための設定（helmet）、入力のチェック、ログ、版の固定 |
| `docs/03_手順書/00_開発環境と版の一覧.md` | `package.json`・`package-lock.json`・`database/compose.yaml` の実際の版 |

資料を直したときの決まり：

- 要件定義の資料（`docs/01_要件定義/`）を直したら、`node tools/build_requirements.mjs` で一番上の `要件定義書.md` を作り直し、一緒にコミットする（`要件定義書.md` は直接書き換えない）
- 同じ内容は1か所だけに書き、ほかからはリンクで参照する
- 部品の版を変えたら、固定しているファイルと `docs/03_手順書/00_開発環境と版の一覧.md` の両方を直し、「変更の記録」に書く

## 3. レビューポイント（人の目で）

デファクトスタンダード（多くの人が使う標準的なやり方）から外れていないか、次のレビューポイントを1つずつ確かめる。
報告では、レビューポイントの**番号（RP-xx）**を使う。「由来」は、そのレビューポイントができたきっかけ（どの見直しで見つかった問題か）。

### 3-1. 処理側（Express・データベース）

| 番号 | レビューポイント | 確かめ方 | 由来 |
|---|---|---|---|
| RP-01 | SQL に値を入れるときは、必ずプレースホルダー（`?`）を使っているか（SQL インジェクション対策） | `backend/src/routes/*.js` の `pool.query` を見る。文字をつなげて SQL を作っていないか | 作ったときの決まり |
| RP-02 | 入力のチェックを処理側でも行っているか。画面側のチェックだけに頼っていないか | `backend/src/validation.js` と、試験の「間違いの入力」 | 作ったときの決まり |
| RP-03 | 失敗したときに、くわしい内容（データベースのエラーの文章など）を返していないか。番号（S04 など）だけを返し、くわしい内容はログに残しているか | `backend/src/app.js` の共通のエラー処理 | 作ったときの決まり |
| RP-04 | `helmet` で安全のための設定（ヘッダー）を付けているか。`X-Powered-By` を返していないか | 試験「安全のための設定（ヘッダー）が付いている」 | 2026-11-03 の見直し |
| RP-05 | パスワードなどの秘密の情報が、プログラムや GitHub に入っていないか（`.env` は `.gitignore` で除外） | `git status`・コミットする前のファイルの一覧に `.env` がないか | 作ったときの決まり |
| RP-06 | 「同じ名前」「使われているカテゴリの削除」「ないカテゴリ」は、先に調べずにデータベースの決まりに任せているか（すり抜けを防ぐ） | `backend/src/routes/*.js` で、先に SELECT して調べていないか | 作ったときの決まり |
| RP-07 | 結果の番号（200・201・204・400・404・409・500）が API 設計書どおりか。201 のときに `Location` を返しているか | 試験と `docs/02_設計/06_API設計書.md` | 2026-11-03 の見直し |
| RP-08 | 止める合図（SIGINT・SIGTERM）を受けたら、受け付け中のお願いを終わらせ、データベースとのつなぎ口を閉じてから止まるか | `backend/src/server.js`。Windows では試験できないので、Linux（EC2）で確かめる | 2026-11-03 の見直し |
| RP-09 | 大きすぎる本文（10KB より大きい）を受け付けないか | 試験「大きすぎる本文は 400（S04）」 | 2026-11-03 の見直し |

### 3-2. 画面側（Vue.js）

| 番号 | レビューポイント | 確かめ方 | 由来 |
|---|---|---|---|
| RP-11 | `<script setup>` と Vue Router の公式のやり方で書いているか | `frontend/src/` | 作ったときの決まり |
| RP-12 | `v-html` を使っていないか（XSS 対策。文字は `{{ }}` で表示する） | `frontend/src/` で `v-html` を探す | 作ったときの決まり |
| RP-13 | 読み込み中・**読み込めなかったとき**・0件のときを、それぞれ正しく表示しているか。「読み込めなかった」のに「0件」「0円」「カテゴリがありません」と表示していないか | 処理側を止めて、画面を開いて確かめる | 2026-11-03 の見直し（高） |
| RP-14 | 保存の途中にボタンを押せなくしているか（二重の登録を防ぐ） | 入力画面の `saving` | 作ったときの決まり |
| RP-15 | 入力の間違いに `aria-invalid`・`aria-describedby` を付けているか（読み上げ機能への対応） | 何も入れずに保存して、間違いのある項目に印が付くか | 2026-11-03 の見直し |
| RP-16 | スマートフォンの横幅（375）で横にはみ出していないか。一覧の見出しと中身の列がそろっているか | 画面の写真を撮って見る（列の幅は `rem` で決める） | 2026-11-02 の画面の確認 |
| RP-17 | 画面に出す文章は `frontend/src/messages.js` の1か所だけにあり、メッセージ一覧と同じ番号・同じ文章か | `messages.js` と `docs/01_要件定義/06_メッセージ一覧.md` | 作ったときの決まり |

### 3-3. 全体（部品・資料・品質チェックそのもの）

| 番号 | レビューポイント | 確かめ方 | 由来 |
|---|---|---|---|
| RP-21 | 書き方のチェック（LINT）で、問題が 0 件か | `npm run lint`（`backend`・`frontend`） | 2026-11-03 の見直し |
| RP-22 | 部品の弱点が 0 件か。開発用の部品の中で使われている部品の弱点も放っておかず、`overrides` などで直しているか | `npm audit`、`package.json` の `overrides` | 2026-11-03 の見直し（minimatch） |
| RP-23 | 部品の版が細かく固定され、`docs/03_手順書/00_開発環境と版の一覧.md` と実際の版が同じか | `package.json`・`package-lock.json`・`database/compose.yaml` と見比べる | 2026-11-03 の版の見直し |
| RP-24 | 資料と実装が食い違っていないか。食い違っていたら、実装を正として資料を直したか | 「2. 資料と実装の見比べ」 | 2026-11-03 の見直し |
| RP-25 | 要件定義の資料を直したら、一番上の `要件定義書.md` を作り直したか | `node tools/build_requirements.mjs --check` | 2026-11-03 の要件定義書の見直し |
| RP-26 | 試験が、お試しデータ（カテゴリ17件・記録28件）を変えていないか | 試験の前後で件数を比べる | 作ったときの決まり |
| RP-27 | **試験や品質チェックのプログラムそのものが、正しく間違いを見つけられるか**（わざと間違いを入れると不合格になるか。数え間違い・実行する場所の間違いがないか） | わざと間違いを入れて実行し、不合格になることを確かめてから元に戻す | 2026-11-03 の見直し（品質チェックのプログラムの間違いを2つ見つけた） |

新しい問題が見つかったときは、同じ問題を二度と見落とさないように、**ここに新しいレビューポイントを足す**（番号は続きから。由来に日付を書く）。

## 4. 報告のしかた

1. 最初に、全体の結果（合格・不合格の数）を1行で伝える
2. 次の表で報告する

   | 区分 | 見つかったこと | 重さ（高・中・低） | 直し方 |
   |---|---|---|---|

3. 直したものと、直していないもの（理由つき）を分けて書く
4. 確かめられなかったこと（例：Windows ではできない確認）は、正直にそう書く
5. コミット・プッシュは、使う人の指示を待つ
